# Расхождения объектов между хостом и клиентом

Отчёт по инструменту `-netdump`. Снят с живых заездов host+client на loopback
(`tools/net-race-test.ps1 -Dump`), на ветке `arcade_network` после мержа PR #1
(`6a2b817`). Числа — из нескольких прогонов по 25–50 с, приводятся типичные
значения, а не один замер.

Связанные документы: `docs/net-sync-inventory.md` (что вообще должно
совпадать), `docs/net-multiplayer-plan.md` (дизайн).

## Как получить данные

```powershell
# весь цикл: поднять хост и клиент, погонять заезд, снять трейсы, сравнить
powershell -File tools/net-race-test.ps1 -Dump -RaceSec 35
```

Вручную:

```
bin\moonshine-runners.exe -nethost  -netrace -netdump
bin\moonshine-runners.exe -netjoin 127.0.0.1 -netrace -netdrive -netdump
node tools/net-trace-compare.js bin\net-trace-host.csv bin\net-trace-client.csv 1
```

`-netdump` пишет по одному CSV на роль. Строка — объект на хост-тик:

| kind | что это | кто пишет |
|---|---|---|
| `R` | гонщик на проводе (упакованный/распакованный `netRacerState`) | хост и клиент |
| `W` | гонщик в мире (интерполяция чужих + локальная своя) | только клиент |
| `E` | реплицируемое тело (class B снаряд / class C актор) | хост и клиент |

Поля: `tick,kind,key,type,variant,px,py,pz,yaw,vx,vy,vz,speed,energy,flags,
lap,cp,place,nstar,mech,feat,pw0..2,st0..2,model,alive`.

Сравнение сводит строки по `(tick, kind, key)`, подбирает лаг репликации и
считает три вещи отдельно: **количество**, **свойства**, **позу**.

## Итог: что совпадает, а что нет

| Слой | Количество | Свойства | Поза |
|---|---|---|---|
| Провод (`R`) | 0 пропущенных полей | — | идентично (0 расхождений) |
| Своя машина (`W` slot local) | — | — | **0.00** |
| Чужие машины (`W` remote) | — | — | ~3–4 юнита (интерполяция) |
| class C акторы (ходячие бонусы и т.п.) | совпадает | type/variant/model — 0 | медиана **0.1–0.4**, среднее 4–8 |
| class B снаряды (`cannon_bomb`) | совпадает (3–4 тика) | 0 | **медиана 20–40, среднее 33–44** |

## Что расходится сильнее всего

### 1. class B снаряды — главное расхождение (исправлено, см. «Исправления»)

`cannon_bomb` (и весь отряд метеоритных class B) — двузначные-сотни юнитов,
с самого рождения снаряда:

```
label         n     lag  xy mean  xy p50   xy p95    xy max   >50  >200  >1024   dvel
cannon_bomb  2090    0     42.92   26.15   42.09  2035.17   43    17     17   27.94
```

Ошибка **не растёт со временем**: уже на возрасте 0–4 тика среднее ~30, к
40–49 тикам ~22. То есть расхождение заложено **в начальных условиях**, а не
накапливается интегрированием.

**Причина (найдена по коду).** `net_fx_create` (`net_fx.cpp`) для метеоритных
class B-типов передаёт в конструктор уже отмасштабированную хостом скорость:

- `Meteorite::Meteorite` (`Meteorite.cpp:20`) делает
  `setGlobalVelocity(V_*(Gravity*0.1f))` — то есть сам домножает `V_`;
- а `netSpawn::vel_*` — это `Vglobal()` хоста, то есть **после** того же
  умножения.

Клиент множит второй раз. Проверка на живом снаряде:

| tick | хост pos | хост v | клиент pos | клиент v |
|---|---|---|---|---|
| 793 | 851,1188 | 76,102 | 842,1176 | **326,439** |
| 797 | 888,1237 | 74,100 | 865,1206 | 76,102 |

Начальная скорость клиента в ~4 раза выше и держится несколько тиков, пока её
не срежет `max_velocity_threshould_meteorite = 140`, после чего позы идут
параллельно со смещением ~30–40 юнитов. Это же объясняет `dvel ≈ 28`.

**Правильный шаблон уже есть тут же**: ветка `NET_ENT_TITANIUM_BALL` строит
тело в покое и потом `setGlobalVelocity(vel)` — ровно то, что описывает
комментарий над `switch`. Метеоритные ветки надо привести к тому же виду
(`new fxlabXxx(model,pos,Vect3f(0,0,0),...)` затем `setGlobalVelocity(vel)`).

Изредка (17 сэмплов из 2090, >1024 юнита) копии оказываются в **разных
местах карты** — независимая коллизия: один снаряд где-то попал/умер, второй
живёт дальше. Это цена «спавн, дальше общая физика»; для короткоживущих
снарядов это и задумано, но на границе видно.

### 2. Чужие машины — задержка интерполяции (ожидаемо)

```
slot 2 remote  best lag -2t  xy mean 4.08  p50 2.90  p95 9.43  max 329.73
slot 3 remote  best lag -3t  xy mean 4.22  p50 3.07  p95 8.63  max 655.27
```

На лучшем лаге (−1…−3 тика) остаётся ~3–4 юнита — линейная интерполяция между
25-мс сэмплами на поворотах. Хвосты (сотни юнитов) — моменты потери снапшотов
и интерполяционной «защёлки» на прыжке/респавне; задержка теперь 3 тика, а
вместо «защёлки» на опоздавшем батче короткая экстраполяция. Своя машина —
строго 0.00, она ставится на хостовую позу (с доводкой на пол-RTT) каждым
снапшотом; см. «Исправления», 10.

### 3. class C акторы — в основном идеально

Медиана 0.1–0.4 юнита, среднее 4–8. Хвосты до ~2000 — перенос через seam
тора и респавн (`setPositionExact` получает абсолютную позу). Репликация
состояния работает; теперь хост шлёт 20 Гц, а клиент интерполирует между
батчами (см. «Исправления», 10).

## Количество и свойства

Количество считается только на тиках, которые клиент **реально получил**;
тики, потерянные в сети, помечаются `skipped`, а не считаются нулём.

```
label           cmp  skipped  count-diff  max|d|  mean|d|
little_spider    31        0          30       2     1.42
cannon_bomb     601       33           3       5     0.01
bonus_man#1    1076       33           1       3     0.00
bonus_man#2    1076       33           1       2     0.00
bonus_man#3    1076       33           1       2     0.00
bonus_man#4    1076       33           1       1     0.00
```

- **Свойства совпадают идеально**: `type`, `variant`, `model` — 0 расхождений
  на ~10 700 общих `(тик, id)`. `alive` расходится в 4–7 строках — это момент
  despawn (тело убито на одной стороне, ещё висит на другой).
- **Количество совпадает**: у ходячих бонусов и снарядов расхождение 1–4 тика
  на ~600–1100, максимум 1–5 объектов — спавн/деспавн со сдвигом в один тик.
- **Провод точен**: `field-mismatched: 0` при 3–4.5% потерь снапшотов — потери
  видны как пропущенные тики, но распакованное состояние всегда равно
  упакованному.

## Режим ботов и несколько миров

`-netbots` гоняет клиентское авто ботом: AI решает локально, решение
захватывается и уходит на хост обычным `netInput`, а применяется через
`net_control` на обеих машинах (см. `-netbots` в `net_game.cpp` и ветку
`bot_input` в `PointControlledObject::control`). Прогон:
`tools/net-race-test.ps1 -Bots -Dump -World N` — 5 миров, по 22 с.

| мир | имя | R полей | slot 1 (локальная) | чужие xy mean | потери снапшотов |
|---|---|---|---|---|---|
| 0 | Запретные Горы | 0 | 0.00 | 4.99–10.15 | 4.5% |
| 1 | Остров Сокровищ | 0 | 0.00 | 4.63–7.80 | 4.4% |
| 2 | Ботаническая Потеха | 0 | 0.00 | 4.99–7.25 | 4.4% |
| 3 | СеноВал | 0 | 0.00 | 4.36–8.44 | 4.6% |
| 4 | Дьявольская Нора | 0 | 0.00 | 3.37–6.58 | 4.4% |

Все заезды `RESULT: PASS`. Клиент шлёт ~700 сэмплов, хост принимает их и
применяет к своей копии слота 1 — машина едет, локальная копия совпадает
точно (0.00 во всех мирах): переданный ввод даёт ровно то же движение, что и
на хосте.

Расхождения по объектам, общие для пяти миров:

- **Провод — ноль.** `field-mismatched: 0`, потери 4.4–4.8%.
- **Локальная машина клиента — 0.00** (одна функция `apply_control` на обе
  стороны).
- **Чужие машины** — лаг интерполяции: mean 3–10, p50 2–6, хвосты до ~2000 на
  потерянных снапшотах. От мира почти не зависит.
- **class B снаряды** (`cannon_bomb` мир 1, `volcanic_bomb` мир 4) — главное
  расхождение позы: mean 9–45, p50 1–27, max ~2040, `dvel` 15–24. Количество
  и свойства совпадают; причина — двойное масштабирование начальной скорости
  в `net_fx_create` (см. выше).
- **`little_spider`** — сломан во всех мирах: у хоста сотни объекто-тиков,
  у клиента 0–4 (мир 3: 408 против 2).
- **`crystal`** (кристаллизация) — зависит от мира: мир 1 почти идеально
  (278/277), миры 0 и 3 теряют на клиенте до половины (мир 3: 774 против 355).
- **`worm`** (мир 2) — обратный перекос: у клиента **больше** (9377 против
  8092 объекто-тиков, 469 тиков расхождения). class C актор живёт/размножается
  на клиенте дольше.
- **Ходячие бонусы** (`bonus_man#1..#4`) и прочие акторы (`butterfly`,
  `dragon`) — количество и свойства совпадают (1–2 тика), медиана позы
  0.1–1.5; хвосты — телепорт бонусмена в `random(2048)` после подбора.

Арканы бота. Бот-клиент кастует сам (`AI_ArcaneQuant`), и каст уходит на хост
**тем же путём, что у живого игрока**: `mchArcaneData::fxlabStart()` →
`mchNetArcaneCast` → событие `NET_EV_ARCANE_CAST` (MSG_EVENT). Кнопки
`NET_BTN_ARCANE*` в `netInput` для этого не годятся — они мёртвые,
`read_input()` их не заполняет. Хост проигрывает каст на своей копии слота и
рассылает визуал; клиент строит только визуал, тел не дублирует.

Прогон 5 миров (22 с), арканы бота-клиента:

| мир | кастов клиента | применено хостом на слот 1 | дропов `status 0` | строк «только на клиенте» |
|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 0 |
| 1 | 2 | 2 | 0 | 0 |
| 2 | 5 | 5 | 0 | 0 |
| 3 | 2 | 2 | 0 | 0 |
| 4 | 1 | 1 | 0 | 0 |

То есть арканы бота ходят как игроцкие, без локального дубля. Кастов немного,
потому что у машины клиента в тестовом конфиге мало активных аркан.

## Исправления

### 1. class B снаряды — двойное масштабирование скорости (исправлено)

`net_fx_create` передавал в конструктор уже отмасштабированную хостом
скорость, а `Meteorite` домножает `V_*Gravity*0.1` ещё раз — копия рождалась
в ~4 раза быстрее. Теперь **все** метеоритные ветки строятся в покое и
получают хостовую скорость через `setGlobalVelocity(vel)`, как уже было у
`TitaniumBall` (`net_fx.cpp`).

Проверка: `volcanic_bomb` (мир 4) `dvel` 16.1 → 1.8, средняя ошибка позы
14.6 → 3–10; `cannon_bomb` начальная скорость на клиенте теперь совпадает с
хостовой (245 u/s в момент спавна), `dvel` 23 → 6.5.

Остаток у `cannon_bomb` (~30 юнитов) — не начальная скорость, а **отставание
на ~2 тика**: снаряд реплицируется «по рождению», без состояния, и за время,
пока спавн дошёл, хост уже пролетел 30–40 юнитов при 250 u/s. Это цена
birth-only репликации для быстрых тел, а не баг.

### 2. Владелец class B-тел (тот же механизм — исправлено)

У class B с `OwnerProtection` (`LittleSpider`, `Crystal`, метеориты) клиентская
копия рождается **на месте своего кастера**. Без владельца такой объект бьёт
сам себя: паучок убивает себя тем же кадром, кристалл повреждается. Хост
задаёт владельца (`op->set_owner(ProtectionID,ProtectionTime)`), но в спавне
владелец не передавался (`owner_slot` всегда 255).

Исправлено:
- хост пакует `owner_slot` (body id владельца → слот рейсера, через
  `Body::ID`, который машинно-локальный) и `protect_ms` (остаток защиты);
- клиент резолвит слот обратно в **свой** `Body::ID` и зовёт
  `set_owner(id, protect_ms)`;
- `netSpawn` получил поле `protect_ms`, `NET_PROTO_VERSION` 10 → 11.

Проверка (5 миров): `little_spider` и `crystal` совпадают по количеству
(0–12 расходящихся тиков на ~100–500 сравнимых, хвосты — спавн/деспавн), тогда
как раньше у хоста были сотни объекто-тиков, а у клиента единицы.

### 3. Черви и залипание акторов (исправлено)

Три отдельные причины:

1. **Двойная регистрация.** Клиент заводил второй экземпляр сущности с тем же
   `entity_id` (видно в трейсе: `825 827 827 828 828...`), и оба рисовались и
   считались. Причина — спавн, пришедший на уже отслеживаемый id (переотправка
   при подключении или гонка с деспавном). Теперь `net_fx_create` игнорирует
   спавн уже известного id.
2. **Залипание за радиусом.** Актёр, ушедший за `NET_ACTOR_SPAWN_RADIUS`, больше
   не обновлялся, но и не деспавнился: у клиента оставался замороженный
   «призрак». Так подбор бонусмена (телепорт в `random(2048)`) оставлял мужика
   на старом месте навсегда. Теперь за радиусом хост шлёт деспавн и выдаёт
   **новый** id на респавн.
3. **Переотправка при подключении** для акторов уже была (`net_fx_resend_actors`).

Проверка: `worm` (мир 2) 7378/7354, 2 расходящихся тика (было 470), медиана
позы 0.04; `bonus_man` — счёт совпадает.

### 4. Области — источники поля (исправлено)

`slime_circle`, `red_track`, `damage_sensor` — это не тела, а `FieldSource` в
отдельной сетке полей: `BodyDispatcher::createBody` их не видит, и до провода
они не доходили вообще. Добавлена репликация:

- хук в `BodyDispatcher::attachFieldSource`/`deleteFieldSource` (хост
  регистрирует источник, шлёт спавн/деспавн под своими area-типами
  `NET_ENT_SLIME_CIRCLE`/`_RED_TRACK`/`_DAMAGE_SENSOR`);
- радиус едет в `model_id` (четверть-единицы), подтип слизи — в `variant`;
- клиент строит `CircleMapSource`/`SensorFieldSource` и зовёт
  `Mdisp->attachBaseObject`;
- при подключении источники переотправляются (иначе созданные до входа клиента
  терялись);
- движение и смена радиуса тоже передаются: `moveFieldSource`/
  `changeFieldSource` зовут `net_fx_field_update`, который шлёт обновление
  (тот же netSpawn с тем же id) не чаще 10 Гц и только при реальном изменении;
  клиент по повторному id двигает существующий источник, а не создаёт дубль;
- силовые поля арканов (вихрь, магнит, притяжение, пузырь) тоже реплицируются
  под типом `NET_ENT_FORCE_FIELD` с подтипом в `variant`. Течения/ветер
  (`Stream`/`Wind`) не передаются: их сила задаётся вектором, которого в
  описании поля нет.

Исключение: `RedTrackSource` — **визуальный шлейф** за машиной, тысячи
короткоживущих копий. Его репликация заливала очередь спавнов и вытесняла
паучков; не реплицируется (косметика локальная).

Проверка (мир 2): `slime_circle#4` 619/618, `slime_circle#2` 114/114, медиана
позы 0.00; `damage_sensor` в этих мирах не встречался.

### 5. Слизь: клиент больше не крутит машину сам (исправлено)

Клиент «дёргался» после слизи и уводил камеру: `Mechos::slime_obstacle()`
(а также `animal_obstacle`/`kinetic_impulse`) начинали локальный прокрут через
`startRotation()`. У клиента поза машины приходит снапшотом от хоста, и
локальный прокрут с ним конфликтует: направление берётся из локального ГСЧ,
два вращения могут идти в разные стороны, накопленный угол никогда не
достигает цели — флаг `ROTATING` не снимается, `rotation_quant` продолжает
крутить машину, снапшот её тут же возвращает, камера следует за рывками.
Теперь `startRotation()` на сетевом клиенте (`mchNetGame && !mchNetHost`) —
no-op: прокрут делает хост, клиент показывает его через снапшоты.

### 6. Выход из запущенной сетевой игры (исправлено)

Меню по Escape в сетевом заезде переиспользует обычный экран паузы, чей пункт
«Выход» шлёт `ACS_EXT_FREE_RESOURCES` → `mchFreeResources()` и меняет экран;
«Прервать/Заново» дополнительно зовут `mchResetRacers()`/`mchFreeResources(1)`.
Пока заезд живой, это освобождает мир из-под работающей симуляции и роняет игру
(и у клиента, и у хоста). Исправлено: при `mchNetMenu` события
`ACS_EXT_FREE_RESOURCES`/`ACS_EXT_ABORT_RACE` не выполняются, а `ACS_EXT_QUIT`
выставляет `QuantCode = -1`; обработчик меню в `mechosoma.cpp` по этому коду
закрывает меню и уходит в главное меню (`RTO_MAIN_MENU_ID`, через `Finit` →
`mchNetFinit`). Закрытие окна (`SDL_QUIT`) тоже сперва зовёт `mchNetFinit`.

### 7. Визуалы арканов, которые не снимались (исправлено)

См. `docs/net-sync-inventory.md`: FireGarden (003, «огненная стена»), RageSlime
(004), FuryFungus (005), FireStone (024) и SnowFall (064) строили длительные
модели-зеркала напрямую через `fxlabClientD->CreateObject()`, без метки
owner/arcane, поэтому `NET_EV_ARCANE_STOP_VISUAL` их не находил и они оставались
на трассе после конца заклинания. Переведены на `fxlabClientArcaneNew()`.

### 8. Детали и сборка мехоса после взрыва (исправлено)

Две связанные расходимости, обе от того, что клиент ведёт свою машину
состояний «взрыв — сборка» независимо.

**Перемешанные детали/заклинания.** При сборке мехос притягивает
*ближайшую* свободную деталь каждого типа (`BodyDispatcher::searchPart`),
поэтому две машины, взорвавшиеся рядом, могут обменяться деталями — а на
трёх «заклинательных» деталях лежат арканы. Обломки у хоста и клиента
разлетаются по своему RNG, наборы деталей расходятся, и
`net_apply_event` на хосте разрешал каст клиента по индексу детали на
*хозяйском* экземпляре машины: клиент жмёт одно заклинание, а стреляет
другое. Теперь хост шлёт `M3D_KIND` каждой активной детали в снапшоте
(`part_kind[]`, без битов морфа/активации — они визуал заклинания, а не
другая деталь), а клиент пересобирает машину под него через
`Mechos::net_sync_parts()`, когда хост сообщает её собранной. Аркан
однозначно определяется видом детали (`mchGetPart` берёт меш из
`MeshLibrary` по `M3D_TOTAL_TYPE(kind, type)`, а `arcaneData` запечена в
меш), так что совпадение вида — совпадение и заклинания. Тот же механизм
чинит HUD-полосы чужих машин.

**Сборка на ходу.** `net_apply_state` запускал последовательность только
на переходе `NORMAL → STAYING_PERSONAGE` и дальше не вмешивался. Если
клиент отставал от хоста, он продолжал собирать детали, уже ведя машину
позицией из снапшота — «бот собирается на ходу». Теперь:
`net_apply_state` заводит последовательность на *любом* не-NORMAL
состоянии (кроме `FORMIC_TRANSPORTED_MECHOS`), а когда хост сообщает
`NORMAL_MECHOS`, `net_sync_parts` немедленно доводит машину до собранной
(`registerGeometry`), так что «собирается и едет одновременно» не может
длиться дольше одного снапшота.

Тест без клавиатуры: `-netdestroy` валит две соседние ботовые машины через
~3 с после старта, чтобы прогнать эту последовательность (см.
`tools/net-race-test.ps1`).

Клиентская пересборка — это подмена, а не сборка: детали своего разбитого
мехоса клиент не собирает, а заменяет. Поэтому своя же разбитая деталь,
оставшись лежать, превращалась в вечный мусор на трассе. Теперь у `Part`
есть `owner_mechos` (ставится в `detachPart`), и `net_sync_parts` перед
пересборкой зовёт `BodyDispatcher::deletePartsOf(this)` — сносит ровно
свои разлетевшиеся детали (чужие, уже кем-то притянутые, не трогает).

Заодно место клиента в гонке стало хозяйским. Клиент считает пересечения
линий своей машиной сам — иначе не проигрывается анимация сбора на
чекпоинте — но его счётчик может уехать на чекпоинт вперёд хозяйского
(проверено: локально C3 при хозяйском C2, и наоборот). А звёзды/буквы на
чекпоинте читаются по `Lap/Checkpoint`: сдвинутый счётчик оставлял клиента
«впереди» до конца заезда, и звёзд показывалось 5 вместо 2 у 4-го места.
Теперь `getCheckpointNStar`/`setCheckpointNStar` и ранжирование мест
(`CheckRacerPlace`/`CheckRacerPlaceHS`) берут `Lap/Checkpoint` локальной
машины у хоста (`mchNetRacerHostStanding`, значения из снапшота), а сам
локальный счётчик не перетирается — анимация сбора сохраняется.

Чужие машины клиент больше не считает сам: `CP_Quant` пропускает удалённые
(их пересечения — из снапшота), иначе локальный счётчик перетирался
следующим снапшотом и два счёта мигали друг против друга — отсюда
«иногда не то количество». Раз удалённый проход больше не дёргает пересчёт,
счёт звёзд на чекпоинте обновляется по отпечатку хозяйских `Lap/Checkpoint`
(`net_stand_fingerprint`), раз на изменение, а не каждый снапшот.

Диагностика в `net-client.log`/`net-host.log`: строка `setNStar:` на каждый
пересчёт (раса, локальный и хозяйский `Lap/Checkpoint`, место, `cp`, сколько
звёзд записано, `pl` и таблица всех машин) и `pass:` на каждый проход
чекпоинта. Лог append-only, так что порядок строк — порядок событий.

Сам счёт звёзд в сетевом заезде теперь по месту, как на стартовом
чекпоинте: `ChStarMAX - place` (4-е место → 2), а не по строгому
`Lap/Checkpoint`, который на одном с лидерами чекпоинте читался как 5.
Строгое ранжирование осталось в одиночной игре; хост и клиент считают
одинаково.

### 9. Чужие машины вставали на мост (исправлено)

Клиент ставит чужие болиды на хостовую позу через интерполяцию
(`net_interp_apply`), и та звала `Body::setPosition` — вариант с «посадкой на
землю»: он пересчитывает z запросом `tri_map->H(x, y, z + 20)` и кладёт тело на
поверхность. Запрос возвращает *высшую* поверхность ниже границы, а под мостом
это настил, а не дорога, — и чужая машина под мостом поднималась на него
(в диагностике сдвиг z доходил до 36–42 юнитов, там где обычная посадка ~10).
Своя машина этого не делает: она уже ставится через `setPositionExact`
(`net_apply_snapshot`).

Теперь оба пути — `net_interp_apply` (все ветки) и `net_reconcile_local`
(снап при расхождении >60) — используют `setPositionExact`: z хоста
принимается как есть. `setPositionExact` по-прежнему зовёт `setPositionInit`
(сброс скоростей/сил), а `setGlobalVelocity` тут же возвращает хозяйскую
скорость, так что поведение между снапшотами не меняется.

Проверено: `-nettest` PASS; хост + клиент с ботами, миры 1 и 2,
`-netfinish 12 -netleave` — заезд идёт, пост-гоночные маркеры на месте,
падений нет.

### 10. Дёрганая картинка: акторы, чужие и своя машины (исправлено)

Три источника рывков, и все — из «положение приходит с сервера».

**Акторы (падающие бонусы, существа).** Хост слал позу на 10 Гц, а клиент
применял её сразу по прилёту, без буфера (`net_fx_apply_actor_state`), то есть
бонус «телепортировался» каждые 100 мс. Теперь у акторов свой буфер
интерполяции, как у гонщиков: хост шлёт 20 Гц, клиент копит 3 сэмпла и рисует
с задержкой 4 тика (100 мс), интерполируя x, y, z и yaw. `net_fx_apply_actors`
зовётся раз в кадр из `mchNetQuant`; на хосте это no-op.

**Чужие машины.** Интерполяция уже была, но задержка в 2 тика не переживала
потерю снапшота: клиент «замирал», а потом прыгал. Задержка — 3 тика, и вместо
замирания короткая экстраполяция по последней скорости (до 6 тиков).

**Своя машина.** Клиент ставил её на хостовую позу через `setPositionExact`
каждый снапшот (40 Гц). `setPositionExact` зовёт `setPositionInit`, а тот
`clearVelocities()` — обнуляет и **угловую** скорость. Сорок раз в секунду
скорость поворота падала до нуля: это и была дрожь. Теперь поза пишется новым
`DynamicBody::setPoseExact`, который меняет только место и курс, оставляя
скорости, силы и скорость поворота на месте; хозяйская скорость всё так же
возвращается через `setGlobalVelocity`. Дополнительно поза доводится на пол-RTT
вперёд по хозяйским скорости и замеру `netSession::host_rtt()` — иначе
устаревшая на время пути туда-обратно поза тянула машину назад каждый снапшот
(пила, заметная только на реальной задержке). `net_reconcile_local` остаётся
запасным вариантом на пропуск снапшотов/телепорт (снап >60).

Проверено: `-nettest` PASS; хост + клиент с ботами, миры 1 и 2,
`-netfinish 20 -netleave` — заезд идёт, поле едет (`5 of 5 racers moved`),
пост-гоночные маркеры на месте, падений нет, локальных «snapping» — 0.
Отдельно проверен клиент без ботов (`-netdrive`): тоже 0 снапов и корректный
пост-гоночный выход.

## Открытые аномалии

- **`crystal` и `little_spider`** изредка теряют часть копий на клиенте:
  class B-тела уничтожаемы, а симулируются независимо («по рождению»), поэтому
  при столкновениях разъезжаются и умирают в разные моменты. Убрать это можно
  только переведя их в class C (репликация состояния) — отдельная задача.
- **Области двигаются и меняют радиус** (`net_fx_field_update` из
  `moveFieldSource`/`changeFieldSource`, троттлинг 10 Гц по факту изменения).
- **`NET_ENT_DEBRIS`/`NET_ENT_WHALE`** не реплицируются: обломки —
  статика/косметика, кит — не тело.

## Что логируется, а что нет

Полный перечень — в шапке `tools/net-trace-compare.js`. Кратко:

- **Логируется** (E): class B — `cannon_bomb`, `volcanic_bomb`, `fire_bolide`,
  `snow_ball`, `sleepy_mortar`, `minor/major_bonus`, `titanium_ball` и
  factory-«умные» (`smart_fireball`, `smart_lightningbolt`, `suicide`, `clown`,
  `evil_eye`, `tomato`, `crystal`, `bubble`, `little_spider`); class C —
  `bonus_man#1..#4` (ходячие бонусы), `butterfly`, `wicked_butterfly`,
  `caterpillar`, `worm`, `dragon`, `frog`, `shark`, `fish`.
- **Логируется отдельно**: тела гонщиков и их гоночные параметры (R/W).
- **Логируется теперь и `E`-полем**: динамические источники поля
  (`red_track`, `slime_circle`, `damage_sensor`) — центр в колонках позы,
  радиус в колонке `speed`.
- **Не логируется**: статичная геометрия трассы (бонусные боксы, шестерни,
  камни, дебрис) — строится из одного загруженного мира; части мехоса и
  колёса; class D косметика (пыль/следы/партиклы) и звук; глобальное состояние
  гонки.

Чтобы сверять количество статичных объектов, нужен дамп **всего** списка тел
`Mdisp` — у `BodyDispatcher::total_bodies` сейчас нет публичного перебора
(понадобится метод-энумератор).
